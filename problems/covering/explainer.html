Part 1 · Codes

Two different jobs a code can do

A computer stores data as strings of bits. A string of length n is a list of n zeros and ones. Noise flips some of those bits.

A code is a chosen subset of all the possible strings. We call the chosen strings codewords. You send only codewords. If noise flips a few bits, the result is usually not a codeword. The receiver then looks for the nearest codeword.

Distance

The distance between two bit strings is the number of positions where they differ. For example, 10110 and 10011 differ in positions 3 and 4, so their distance is 2.

Codes get designed for two opposite jobs.

The first job is error correction. Here you want the codewords far apart. If every pair of codewords has distance 5 or more, you can repair up to 2 flipped bits without any doubt. This is the packing problem. It asks you to pack many balls into the space without overlap.

The second job is covering. Here you want every string in the whole space to sit close to some codeword. No string is allowed to be far from everything. This page is about the second job only.

Covering radius

The covering radius of a code is the largest distance from any string to its nearest codeword. A covering radius of 2 means this: you can reach a codeword from any string in at most 2 bit flips.

Covering codes are useful because they let you round. Take any string, move to the nearest codeword, and store the codeword instead. You lose at most 2 bits of accuracy. That idea shows up in data compression, in steganography, and in the football pool problem, which asks how few betting slips guarantee a near-win.

The interesting question is cost. Codewords are cheap to store when there are few of them, but few codewords leave big gaps. So we ask a minimum question. How short can a code be and still have covering radius 2?

Part 2 · Syndromes

Why the whole problem fits in 1024 numbers

The question above involves 2ⁿ strings. That is far too many to search. The problem gets much smaller once we restrict to linear codes.

Linear code

A code is linear when the XOR of any two codewords is again a codeword. XOR means bit-by-bit addition where 1 + 1 = 0. It is ordinary addition modulo 2.

A linear code has a compact description. You write down a matrix H with r rows and n columns, filled with zeros and ones. A string x is a codeword exactly when Hx = 0, computed modulo 2. We call r the redundancy. The code then has 2ⁿ⁻ʳ codewords.

Syndrome

The syndrome of a string x is the vector s = Hx, computed modulo 2. It has r bits, so there are 2ʳ possible syndromes. A string is a codeword exactly when its syndrome is zero.

Now comes the step that makes the problem finite. Flip bit i of a string. The syndrome changes by exactly column i of H. Flip two bits, and the syndrome changes by the XOR of those two columns.

So the distance from x to the nearest codeword is the smallest number of columns that XOR to the syndrome of x. This gives the whole problem in one line. Write S for the set of columns of H.

{0}  ∪  S  ∪  (S + S)  =  all 2r syndromes Covering radius 2 means every syndrome is zero, or a column, or the XOR of two columns.

Set r = 10. There are 1024 syndromes. The columns are themselves 10-bit numbers, so they live in the same set of 1024 values. The problem is now completely concrete.

Choose as few 10-bit numbers as you can, so that their pairwise XORs reach all 1024 values.

Part 3 · The search

Counting says 45. Reality says 51.

Start with a count. Take n columns. Then you get one empty sum, n single columns, and n(n−1)/2 pairs. Together they give

1 + n + n(n−1)/2  ≥  1024 You need at least this many representations to have any chance of covering 1024 syndromes.

Solve it and you get n ≥ 45. This is the sphere-covering bound. It is a lower bound, and nobody has ever found a code that reaches it here.

The count is optimistic because it assumes no two pairs collide. Real column sets collide constantly. In the 50-column matrix on this page, the 1225 pairs produce only 986 distinct results. That means 239 pairs land on a value another pair already reached. Every collision is wasted reach.

So the true answer sits above 45, and finding it is hard. Kaikkonen and Rosendahl published a 51-column matrix in 2003. That has stayed the shortest published answer for over twenty years. A search run in 2026 found a 50-column matrix. The map below is that matrix.

A set that breaks when you remove any one element is called minimal. In the geometric language of this field, these 50 columns form a minimal 1-saturating set in the projective space PG(9,2). Nobody can shorten this matrix by simply deleting something.
Part 4 · The seed

One column, multiplied

Going from 51 to 50 looks like a small win. It is not, and the reason lies in how the published tables get built.

Davydov, Marcugini and Pambianco published the current best bounds in November 2025. Their tables list a value for every redundancy r up to 64. They do not find each value separately. Instead they use a construction that grows a short code into a long one.

nnew = 2m(nold + 1) − 1     rnew = rold + 2m Apply this repeatedly and one short code produces an infinite family of longer ones.

Every entry in their radius-2 table grows from the same starting point. That starting point is the 51-column matrix at r = 10. Their own proof calls the structure of that matrix "very important for the next iterative process."

So the value at r = 10 is a multiplier, not just a table entry. Improve it by one column and you improve every entry that grows from it. You also improve the limit that the whole family approaches.

The automated search that found this matrix wrote "do not claim f(2)" in its own notes and then stopped. The caution was correct for an unsupervised program. But it treated the table as a list of numbers to beat. It never asked what the table was made of.
Part 5 · Blocks

A shorter matrix is not enough

The growth construction needs a second thing from its starting matrix. It needs a way to sort the columns into blocks.

Valid block split

Sort the columns into blocks. The split is valid when every syndrome still has a representation that uses columns from different blocks. Write p(H) for the number of blocks.

The number of blocks controls how much you can grow the code in one step. The construction requires p(H) ≤ 2ᵐ ≤ n. Fewer blocks means larger steps are legal.

The published 51-column matrix needs 11 blocks. The 50-column matrix accepts 10. That is both smaller and safely under the 16 that the first growth step requires.

Finding the split is a graph coloring problem wearing a disguise. The 821 syndromes with exactly one pair force those two columns into different blocks, which produces a graph with 821 edges. The other 152 syndromes are looser. Each one only needs at least one of its several pairs to be split.

The matrix also has a third property that the later growth steps need. Three of its columns XOR to zero, and those three sit in three different blocks. The matrix has ten such triples.

The fourth column of that table has a name. It is the covering density: the total number of representations divided by the number of syndromes. It is the average number of ways each syndrome gets reached. It can never drop below 1. A value near 1 means an efficient code.

As redundancy grows, this family drives the density toward 2601/2048 ≈ 1.2700. Compare that to the record before it.

Part 7 · Limits

What this does not prove

  • 50 is not proven best. The counting bound only says ℓ₂(10,2) ≥ 45. Five columns of room remain unexplored.
  • The failed search at 49 proves nothing. One run stopped with 7 syndromes uncovered. That describes the search program. It says nothing about whether 49 columns exist.
  • Nobody has confirmed priority yet. The published table says "best as far as the authors know". Somebody must check the older workshop proceedings and the field bibliography before anyone claims a record.
  • The far end of the family is weaker. The steps at m = 4 and m = 5 got checked exhaustively. Later steps rely on a bound from the paper instead of a directly computed block split. A referee will ask about this first.
  • The big question stays open. Nobody knows the smallest density any family can reach. It might be as low as 1. This work moves an upper limit and nothing else.
  • Nearby cases did not fall. The same search failed at redundancy 8 and 9. It missed 3 and 8 syndromes there.

The part worth keeping

Search and proof are separate jobs here, and that separation is what makes the result safe.

A random search only had to succeed once. It did not have to explain itself. Everything after that point is a certificate: a table of 500 bits that anyone can check by hand or by machine in under a minute. The check does not trust the search, the searcher, or the story.

That is a good property to look for when you point an automated search at an open problem. Ask whether a success would be cheap to verify. Here it is.
